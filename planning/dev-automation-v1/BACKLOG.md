# `/to-tickets` — Proposition de découpage V1 (`EPURE` / `Giskard-AI/epure`)

**Statut :** approuvé et publié sur GitHub (`Giskard-AI/epure`) — spec parente [#1](https://github.com/Giskard-AI/epure/issues/1) et 38 sous-issues ([#2](https://github.com/Giskard-AI/epure/issues/2) à [#39](https://github.com/Giskard-AI/epure/issues/39), soit `#N = id_local + 1`) étiquetées `ready-for-agent` avec relations natives `sub_issues` et `blocked_by`.

**Source :** spec V1 et ADR-0001 à ADR-0025 (Q1–Q83). **Approche :** tranches verticales testables, dépendances bloquantes minimales.

Les numéros sont des identifiants **locaux**, pas des numéros d'issues GitHub. Chaque ticket est un fichier séparé dans `issues/`.

## Validation demandée par le skill

1. La granularité convient-elle (tickets trop gros ou trop petits) ?
2. Les dépendances bloquantes sont-elles correctes et minimales ?
3. Faut-il fusionner ou subdiviser certains tickets avant de les marquer `ready-for-agent` ?

## Règles de publication après approbation

- Remplacer l'état `draft` par `ready-for-agent` pour les tickets approuvés ; les tâches bloquées restent non exécutables tant que leurs bloqueurs ne sont pas satisfaits.
- En cas de migration vers GitHub : créer les tickets en ordre de dépendance, les relations natives de blocage et, le cas échéant, la hiérarchie parent/enfant ; ne pas traiter les numéros locaux comme des numéros GitHub.
- Ne pas publier les tickets avec un LLM actif avant approbation humaine du plan et de sa spec.
- Les branches, issues, PR et checks du projet consommateur restent les sources de vérité à l'exécution.
